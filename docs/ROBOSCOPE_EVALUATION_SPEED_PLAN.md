## 1. 结论

建议保留现有 OpenWAM harness 的原生批量推理、任务队列和结果记录，移植 RoboScope 的环境侧动作队列、资源感知并发搜索和常驻 worker 思路。不要先整体替换框架。

框架公共能力的实施优先级是：

1. 统一性能计时与协议记录，建立模型输入、动作块、历史和会话状态的能力声明。
2. 环境侧维护动作队列与必要的逐步历史；只在需要推理时发送观测。
3. 保留原生动态合批，为不同模型与任务负载自动选择并发和实际 batch。
4. 优化模拟子进程通信，并在初始化一致性通过后引入常驻进程池。
5. 用统一结果、资源和正确性指标验收；文本离线缓存、特定 kernel 等放在模型适配层。

E00/M29、不同视觉 Encoder 实验及后续第三方模型复用上述公共机制。不能把 VPP2 的最优配置或加速比例套给其他模型，也不能让 VPP2 专用文本缓存成为公共调度器的前提。

## 框架级目标架构与接口

```text
任务队列 / 固定评测协议 / 断点恢复
                ↓
环境 worker：逐步执行 + 动作队列 + 视觉历史
                ↓ 仅在重规划时发送必要观测
公共请求队列：按模型实例与兼容输入分组、动态合批
                ↓
模型 adapter：原生预处理 → 原生 batch 推理 → 动作转换
                ↓
返回动作块 → worker 按模型执行长度消费

性能与资源计时贯穿各层；模型专属缓存由 adapter 管理。
```

这里的“公共”指复用同一实现和接口，不要求不同模型同时常驻，也不要求把不同模型请求放进同一个 GPU batch。

### 最小能力声明

在现有模型服务配置上增量补充字段，先让当前 adapter 接入，避免先建设大型插件系统：

| 能力 | 声明或语义 | 调度器的用途 |
|---|---|---|
| 动作块 | `prediction_horizon` 与 `execution_horizon` 分开 | 预测 32 不等于执行 32；每模型保留原协议 |
| 历史 | `history_offsets`，索引单位是实际控制步 | 环境侧维护历史，推理边界上传所需帧 |
| 观测 | 所需相机、状态及可选模态 | 仅传输模型消费的字段；预处理仍归 adapter |
| 原生批量 | 是否真正支持 tensor batch、兼容 shape/配置 | 不支持的模型诚实按单样本执行，不把 Python 循环当 batch |
| 状态性 | 是否需要逐步 observe、是否存在逐 episode cache | 决定能否省略中间请求、如何粘性路由和清理 |
| 缓存 | 是否可离线编码指令、是否存在静态输入特征 | 调度器不依赖具体文本/视觉编码器 |
| 资源配置 | 安全 batch、CPU 线程、可用副本数 | 用实测 profile 提供默认值，不硬编码 128/16 |

对于必须每步接收观测的 recurrent policy，不能只增加一个声明就跳过 observe：需要保留轻量 observe 通道，或继续每步上传所需数据；只有支持本地历史汇聚的模型才可走完整的块级优化。

模型的 resize、拼图、state 维度、归一化、采样器、动作表示继续留在 adapter 内。环境公共层负责按标准环境动作执行，不统一改写模型原生输入语义。

### 会话、合批和调度

- 请求携带 `session_id / episode_id / observation_step`，响应携带对应动作起始步。重置、超时重试或 worker 重建后，旧响应不能被新 episode 消费。
- 每环境只有一个未完成的动作预测，队列长度有上限；环境完成或取消后清理待处理请求和会话缓存。
- 对有视频 KV/recurrent state 的模型，会话绑定同一实例；无状态模型才可跨实例负载均衡。不同 episode 的状态不能混用。
- 合批仅组合相同模型、推理设置及可兼容输入。最大等待时间和最大 batch 联合约束延迟，保留当前单 GPU owner thread 的设备管理方式。
- 先保留现有按任务动态领取的队列；后续可用历史任务耗时减少尾部拖延，但保持任务内部随机数独立并验证结果不受调度顺序影响。
- OOM 处理属于模型适配和调度边界：仅在确认支持安全重试、状态不污染时拆批重试；正式运行记录实际 batch，并用预热 profile 避免长期靠 OOM 探索。

### 性能 profile 可复用，但不能盲用

用模型/配置签名、输入 shape 与历史长度、推理步数、GPU 型号/数量、软件版本、渲染负载和 CPU/内存限制标识性能 profile。相同签名可复用上次最优配置，新模型先短测再运行；正式评测开始后固定配置，避免难以追溯的在线变更。

不同视觉 Encoder 的 token 数、条件帧数与 cache 大小会变化；即使都叫 M29，也不应无条件共用一个 batch 上限。权重仅变化但架构相同时，可复用候选配置，仍需短预热确认。

### 公共层实现顺序与验收实验

| 阶段 | 公共变更 | 首批代表模型与验证 |
|---|---|---|
| F0 | 统一阶段计时、协议签名、能力声明和 profile 格式 | 当前 M29 + VPP2；不改变执行路径，建立各自基线 |
| F1 | 环境侧动作队列、历史 ring buffer、请求步号校验 | M29 历史模型 + 单帧模型；与原路径逐次核对推理输入和消费动作 |
| F2 | 通用合批配置搜索、资源预算与实际 batch 记录 | 至少两个计算/显存规模不同的 adapter；分别寻找最优点 |
| F3 | 通用模拟 `step_chunk`，保留逐步 done、历史、记录和可选 observe | 当前 LIBERO/Plus；固定动作回放逐步对比终止与观测 |
| F4 | 经验证的常驻模拟进程池 | 跨任务 reset、随机状态、噪声与资源泄漏验证 |
| F5 | 按 profile 启用副本、MPS或更快传输 | 只有前面计时显示收益空间时启用 |

F1/F2 可以分别相对 F0 测试，再组合，避免将调参收益误记为通信优化收益。除有历史与无历史两类外，接口验收还要覆盖“不支持原生 batch”和“必须每步 observe”的行为；没有真实 adapter 时用小型协议测试替身验证边界，不能宣称已有真实模型性能结果。

框架验收不要求所有模型都提速同一比例。要求旧 adapter 仍能运行、协议与输入一致、状态和任务无串扰，且每模型报告自己的端到端时间、成功率、实际 batch 与资源峰值。后续模型主要增加 adapter 和实测 profile，不再复制一套队列、通信与调度代码。

以下章节中的 VPP2 日志用于解释公共机制为何值得做；其中 UMT5 预计算、10 步执行和约 4–4.5 小时目标仅属于该模型案例。

## 2. 阅读依据与实际差异

阅读的 RoboScope-Kit 版本：`02318536e3c97656596c0635655bbe3aa9d0750f`，包版本 `0.8.0b15`。

| 机制 | 本地源码实际行为 | 对我们的意义 |
|---|---|---|
| 环境侧动作队列 | `runtime/benchmarks/libero/worker.py:39` 的 `PolicyActionQueue` 只在动作耗尽时构建观测、请求策略 | 可减少缓存动作期间的图像上传 |
| 推理服务 | `server.py:84` 对请求加锁串行分发；LIBERO worker 调用 `act`，没有自动跨 worker 合批 | 不能直接替换我们的动态 tensor batch 服务 |
| 显式 batch 接口 | `policy.py` 的默认 `act_batch` 是逐样本调用 `act` | 接口存在不代表原生批量执行，模型适配器必须覆盖 |
| 传输 | Unix socket，但 `protocol.py` 使用 JSON、NumPy 转 bytes 后 base64 编码 | 不是零拷贝，也不能默认比现有 raw MessagePack 更快 |
| 并发调优 | `runtime/benchmark/autotune.py` 联合搜索 worker/副本，估计 CPU 与显存限制 | 借鉴搜索方法，不能机械照搬默认上限 |
| 常驻 worker | 同一 Python worker 领取多个任务；任务改变会关闭并重建环境 | 可摊薄解释器、模块导入成本；不等于环境始终不重建 |
| 队列与恢复 | 文件原子领取、任务分组、失败重排 | 我们已有 SQLite 动态队列与结果恢复，不必为提速重写 |
| MPS | 可选私有 daemon，管理模型进程并发 | 不减少模型权重/KV 大小，不能解决 VPP2 显存不足 |

RoboScope README 的加速倍数对应其他模型、资源和对照基线，不能套用到已经使用四卡动态 batch 的本项目。

### 必须保留的评测协议

| 项目 | 当前 OpenWAM Plus | RoboScope 本地默认 |
|---|---|---|
| seed | 10000；fresh process 中按既定顺序设全局 seed，不额外调用 `env.seed` | 7；显式 `env.seed` |
| settle | 30 步 | 10 步 |
| 最大步数 | Spatial/Object/Goal 600，Long 700 | 220/280/300/520 |
| VPP2 动作使用 | 预测 32，执行前 10，再规划 | 取决于适配器返回的 chunk |
| 任务初始化 | 每任务新子进程、固定初始化状态索引 0、修正指令后缀 | 常驻 worker，需要重新对齐初始化语义 |

缩短最大步数会让失败轨迹更快结束，但同时改变分数含义。本方案保持当前协议；未来若采用 RoboScope 默认协议，必须单独命名、单独报告，不能与既有结果混算。

迁移适配器还需保留相机只旋转 180° 一次、各模型独立的状态格式和动作归一化：VPP2 原生 8 维状态与 M29 EEF10 不能用同一个 canonical state 直接替换。

## 4. P0：分阶段计时与 VPP2 文本缓存

### 4.1 先把模型服务的时间拆开

增加聚合计时，而非逐步大量写日志：

- 环境：创建/导入、reset/settle、`env.step`、图像处理、父子进程传输。
- 请求：序列化/解码、排队、等待合批、发送/接收。
- 模型：文本 cache miss 与 encoder 搬运、图像预处理/H2D、VAE、CLIP、video prefill、action denoise、后处理。
- 资源：实际 batch 分布、OOM 分块次数、GPU 模型/渲染显存、GPU 利用率、CPU throttling、RSS/PSS、cgroup memory/pressure。

CPU 阶段用单调时钟；GPU 阶段在抽样 profiling 中用 CUDA events，避免生产路径每阶段强制同步。报告总 wall time 与稳定阶段吞吐，不能只报告排除启动后的最佳窗口。

### 4.2 将 UMT5 缓存提前做完

当前 `benchmarks/vla_harness/vpp2_policy.py:62` 的 `contexts()` 遇到未缓存指令时，把整个文本编码器移到 GPU，编码后再搬回 CPU，并执行 `empty_cache`。每个 GPU 副本各自重复积累缓存。这既产生传输开销，也与渲染/视频 cache 争显存。

实施方案：

1. 从准确的评测任务表构建完整 prompt 集合，包含指令后缀修正与 VPP2 原模板。
2. 使用当前权重对应的 UMT5、tokenizer、长度 128 和相同编码路径，预计算特征及 mask。
3. 缓存键包含完整 prompt、权重/配置版本及编码参数；写入 manifest，缺失时明确报错或进入显式受控回退。
4. 服务只加载特征，不再加载完整文本编码器；CPU 只读缓存可由各副本共享读取。
5. 在真实 prompt 上比较缓存值、mask、原始模型输出，确认没有改模板或 padding。

若当前完整 prompt 去重数为 1,549、特征为 `[128,4096]` BF16，主体约 1.51 GiB，另有 mask/索引开销；实施时以实际枚举与 tensor dtype 为准。缓存构建耗时单独记录，同时报告首次端到端与重复评测耗时。

收益未实测，不承诺固定百分比。M29 已有离线 RynnBrain 特征，本项主要针对 VPP2。

## 5. P0：联合调优 worker 数与实际 batch

不要把“128 workers”当成固定最优。128 个渲染环境会争用显存和 CPU，还伴随父进程/模拟子进程开销；机器当前 cgroup CPU 配额为 64 核。

每 GPU 的安全预算应满足：

`模型权重 + KV(batch) + workspace(batch) + 渲染(worker/GPU) + 余量 <= 可用显存`

当前 `vpp2_model_server.py` 在 OOM 后将 microbatch 减半，之后不会自动恢复，因此早期一次内存峰值就可能让整场固定跑 batch8。正式配置应先经过稳定负载预热，避免依靠反复 OOM 选择工作点；日志必须同时记录 requested batch、实际 batch 和 microbatch cap。

分阶段搜索，不运行整个笛卡尔积：

1. 固定四卡各一个 VPP2 实例、batch8，比较 workers 32/64/96/128；如拐点在 32–64，再补 48。
2. 对最好的两个 worker 数，比较 batch8/12/16；只有供给不足或显存限制时才补 batch4。
3. 对最佳组合比较合批等待 2/5/10 ms。长达秒级的模型推理下，这一项优先级低于前两项。
4. 保留 6–8 个有效候选即可；每项测量覆盖初始化及稳定窗口，至少有足够任务让所有 worker 持续工作。

probe 包含七类扰动、长任务与高成本噪声，不只挑 20 步冒烟或简单任务。最终用固定 512 条左右的配对子集确认最好的两个配置；小样本结果仅用于选配置，正式分数仍来自全量。

RoboScope 借鉴点是资源模型与逐步搜索。其默认允许约 15% 相对成功率下降的调优容忍度不适合我们的科研比较：例如基线 90% 降到 76.5% 也可能被放行。这里不能照搬。

M29 单独建曲线，不继承 VPP2 的最优 batch；可从 batch8/16/32、workers32/64/96/128 起步，按显存预筛。

## 6. P1：环境侧动作队列，减少两个传输边界

### 6.1 第一阶段：只减少 worker→模型服务的请求

目前服务已经缓存动作，但 worker 仍在每个控制步上传图像。RoboScope 的 `PolicyActionQueue` 将缓存放在环境侧，因此缓存动作期间不请求策略。

改为每次返回完整预测动作块，worker 只执行前 10 步，之后必须重新规划；不能把预测 32 步全执行了。每个环境步仍执行相同的 `env.step`、done 检查和日志语义。

对 VPP2，按最终完整 10,030 条轨迹汇总：共 2,456,760 个控制步，若每 10 步请求一次，约 249,263 次请求。双路 `256×256×3 uint8` 图像的理论未压缩 payload 从约 899.69 GiB 降到 91.28 GiB，约减少 9.86 倍。这是依据轨迹计算的 payload 估算，不是实测网络流量，也不是总评测时间加速倍数。

对 M29，必须把逐控制步视觉历史移到 worker。当前 `model_server.py:158` 在每步更新历史，用于例如 `[-4,0]` 条件帧；减少请求后仍要上传同一组历史帧，不能只保留上次规划时的图像。不同历史配置需要分别验证。

### 6.2 第二阶段：减少 worker→模拟子进程的 RPC

当前 `libero_plus_env.py:71` 每执行一个动作，就通过 Pipe 返回整份 `env.step` 结果，图像还要跨越一次父子进程边界。

增加 `step_chunk` 命令：在模拟子进程逐步执行最多 10 个动作，任一步 done 或到达剩余 horizon 都立即停止。返回实际执行步数、终止信息及下一次推理所需观测；有录像/逐步记录要求时保留相应数据通道。

M29 在子进程维护历史 ring buffer，返回精确条件帧，避免把全部中间图像又搬回父进程。先完成第一阶段并验证，再做此项。

**这两阶段均不默认跳过渲染。** RoboScope 本地 LIBERO worker 仍逐步调用普通 `env.step`。Plus 的 SensorNoise 等处理可能消耗随机数；中间帧不上传不代表可以不生成。Lazy rendering 是另一个有协议风险的优化，需要单独验证。

## 7. P2：常驻进程池，摊薄每任务启动成本

当前每个 Plus 任务创建新的 Python 模拟子进程；10,030 条任务会反复进行模块导入、初始化和销毁。RoboScope 使用常驻 worker，可借鉴其领取新任务后重建任务环境的结构。

但当前 fresh-process 初始化顺序属于复现协议。常驻进程中的全局 RNG、模块缓存和构造函数调用顺序不同，简单 reset seed 不保证等价。实施前须比对：

- 任务身份、语言、初始模拟状态和首帧 RGB。
- 固定动作序列下每步观测、噪声序列、done 与轨迹长度。
- reset/retry 分支对随机状态的影响与跨任务污染。

如果采用 forkserver，父进程不能提前建立 EGL/CUDA 上下文后直接 fork。先确认可安全预加载的纯 Python 模块与依赖环境，不能为了减少导入时间引入图形上下文继承问题。

常驻进程主要减少启动/导入成本；同时存活的渲染环境数若不变，GPU 渲染显存不会自动降低。若启动成本占比很小，则此项收益有限。

## 8. P3：多副本、MPS 与平台迁移

对 VPP2，优先保持一实例/GPU：权重、视频 KV 与渲染已经接近显存上限，增加副本大概率先撞显存。MPS 不会合并模型权重或 KV。

对 M29，只有 profiling 显示单副本存在可重叠的 GPU 空闲且显存足够，才试每卡两个副本与私有 MPS。CPU、渲染和队列不足也可能限制吞吐，不能把 replicas 当默认解法。

“三卡推理、一卡专门渲染”只作为后续对照，不能先认定更快：会损失一个模型副本，且全部渲染集中一张卡可能 OOM，需要重新测量资源曲线。

完整接入 RoboScope 适合未来统一模型/benchmark 管理，但不是当前最快的提速路线。其包要求 Python >=3.11，当前模拟环境是 Python3.10；若迁移需独立构建运行时、适配协议，并保留原生动态合批，不能直接覆盖现有环境安装。

## 9. VPP2 案例的实验与验收

| 实验 | 相比前一项的变化 | 目的 |
|---|---|---|
| S0 | 当前代码与 128/16 配置；记录实际 microbatch | 对照，与已有完整日志交叉验证 |
| S1 | 离线文本缓存，其他相同 | 分离文本迁移成本 |
| S2 | S1 + 最优 workers/batch | 分离资源争用与合批收益 |
| S3 | S2 + worker 本地动作队列 | 量化每步图像 RPC 成本 |
| S4 | S3 + 子进程 step_chunk | 量化父子进程传输成本 |
| S5 | S4 + 常驻任务进程池 | 在严格初始化验证通过后测启动开销 |

所有实验固定 checkpoint、任务/初态、seed、图像处理、动作执行长度与 horizon；同时记录候选配置与实际配置。S0–S4 不必每组跑一遍全量，先做固定子集，最佳方案再全量。

运行时优化先用固定输入/固定动作回放验证数据与终止语义。更换 GPU batch 可能改变 BF16 数值路径：现有真实观测测试的最大动作差约 0.011，所以不能要求不同 batch 闭环逐比特相同。应固定逐样本初始噪声，检查样本隔离、误差、夹爪决策，并报告配对成功差异和置信区间；子集不足时不能宣称“零精度损失”。

统一指标：

- 同一固定任务集的总 wall time，以及启动、缓存构建、调优与稳定执行的分项时间。
- 完成任务/s、环境 steps/s、模型 chunks/s、实际 batch 分布和尾部时间。
- 总体及各扰动成功率、错误数、轨迹长度；不能通过更早失败提高吞吐。
- CPU/内存/显存峰值与压力；正式运行不依赖持续 OOM 重试。

## 10. 速度目标与实施边界

先以约 5.5 小时的这轮四卡 VPP2 评测为参考，第一阶段目标是验证能否进入约 4–4.5 小时区间，属于待验证工程目标，不是测量结果。此前单卡 batch8 短测约 4.35 samples/s，而完整运行每卡约 3.11，说明有值得查明的差距，但两种负载不同，不能把差距直接算成保证收益。

网络 payload 减少约十倍也不意味着评测快十倍。例如该部分只占总耗时 30%，即使自身快十倍，总体也只有约 1.37 倍。是否能进一步到 2–3 小时，需要实际分阶段 profiling 支持；现阶段没有证据承诺。

已按上方进度修改公共评测代码；没有修改 RoboScope-Kit，没有启动 GPU 训练/评测或停止已有 GPU 任务。正式性能测试应在独占、同等资源条件下进行。
